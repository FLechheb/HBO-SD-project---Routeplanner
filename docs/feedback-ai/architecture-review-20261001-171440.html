Problem: interpreting a journey requires reading orchestration, result rendering, route types, and time arithmetic; route decisions are exercised through rendering.

Solution: concentrate existing route interpretation behind one small interface while keeping page coordination in App and display in the result module.

  • Locality: journey rules change together
  • Leverage: tests exercise complete outcomes
  • Depth: display learns fewer rules
Evidence, deletion test, and verification target

App submission calls setCurrentPage("results") and logs inputs; RouteResult then looks up stops and classifies facilities. Avoid merely moving that rendering into another shallow module.

Deletion test: a journey module earns its keep only if deleting it puts route rules back into callers; the existing time helper need not be deleted or made independently configurable.

Test surface: exercise missing stops, station order, facility classification, and transfer-time arithmetic through the journey interface; retain a rendered submit-to-result check. Preserve current outcomes until requirements say otherwise.

Problem: finite choices live in the editor while persistence accepts any string facilities and numeric transfer time, so a restored profile can disagree with its controls.

Solution: put profile choices and stored-data validation together; retain local draft ownership and make persistence outcomes explicit before deciding navigation.

  • Locality: one profile validity policy
  • Leverage: editor and storage agree
  • Depth: callers avoid storage details
Evidence, deletion test, and verification target

The editor defines transfer choices including [0, 5, 10, 15]; storage validates primitive shapes rather than membership. App reconstructs the same profile from separate arguments.

Deletion test: removing the profile policy would spread validity decisions back across editor and persistence. Do not add a separate pass-through module for each operation.

Test surface: load malformed and unsupported stored values, round-trip a valid profile, edit without committing, cancel, and handle storage write failure. Browser storage and an in-memory test adapter justify a seam only when both are actually used.

Problem: the unused paths disagree about endpoint configuration, transport, and data shape; sharing them now would hide unresolved differences rather than create depth.

Solution: first choose the intended route contract, then concentrate its transport details in one module; keep remote shapes inside its adapter and the active route model near journey interpretation.

  • Locality: transport knowledge stays contained
  • Leverage: one consistent failure policy
  • Depth: callers avoid raw formats

Conditional recommendation, not an instruction to add remote planning. Coordinate and station requests are not interchangeable adapters. Do not introduce a general transport framework.

Deletion test and verification target

Deletion test: today the inactive transport graph can disappear without changing the rendered flow. Once a route adapter is used, its value is keeping encoding, decoding, configuration, and failures out of callers.

Test surface: request mapping, configured endpoint, malformed responses, non-success responses, and planner behavior with a test adapter. Define expected outcomes before implementing this work.
